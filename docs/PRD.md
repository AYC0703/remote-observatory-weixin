## 2. 项目背景

远程天文台（高校、科研机构或天文社团的远程观测设备）是稀缺资源：设备数量有限，可用于观测的夜间时段有限，且观测计划通常需要提前协调。

依靠邮件、即时消息或线下表格进行预约，存在以下问题：

1. **申请分散**：申请散落在邮件与聊天记录中，难以统一管理与追溯。
2. **时段冲突**：同一台设备、同一时段可能被重复批准，导致设备撞车。
3. **过程无记录**：审批过程缺乏留痕，责任不清晰，出问题无法复盘。
4. **缺少统计**：无法回答「哪台设备最忙」「通过率多少」「需求趋势如何」等问题，难以支撑资源规划。

本系统把「申请 → 审批 → 统计」全流程线上化，用于解决上述问题。

## 3. 项目目标

1. 为观测者提供简洁的在线申请入口，**在提交前即可知道时段是否已被占用**。
2. 为管理员提供集中的待办队列与设备时段占用视图，**从机制上避免重复批准**。
3. 完整记录每一次状态变化（谁、何时、做了什么、为什么），**全流程可追溯**。
4. 提供可视化统计与报表导出，支撑设备与资源的规划决策。

## 4. 术语定义

| 术语 | 说明 |
| --- | --- |
| 申请 | 一次观测时段使用请求，拥有全局唯一申请编号 |
| 使用时段 | 申请的起止时间（精确到分钟），**允许跨日**（如 22:00 至次日 02:00） |
| 观测设备 | 可被申请的观测设备（各类望远镜 / 射电望远镜），由管理员维护 |
| 时段冲突 | 同一设备上两个申请的时段区间存在重叠，且这两个申请处于「待审批」或「已通过」状态 |
| 状态历史 | 单条申请从提交到终态的全部状态变更记录 |
| 审计日志 | 系统级操作流水（注册、登录、退出、提交、审批、撤回、设备维护等） |
| 通过率 | 已通过数 /（已通过数 + 未通过数），不含待审批与已撤回 |

## 5. 用户角色与权限

| 角色 | 获取方式 | 权限范围 |
| --- | --- | --- |
| 普通用户（user） | 自助注册 | 提交申请、查看并撤回自己的申请、查看自己的状态历史、修改自己的密码 |
| 管理员（admin） | 系统预设（不可注册） | 全部申请查看与审批、设备管理、时段日历、统计分析、CSV 导出、审计日志 |

权限原则：

- 界面按角色渲染，普通用户不会看到任何管理员入口。
- 所有权限以后端校验为准，前端隐藏仅是体验优化；越权请求返回 401 / 403。
- 普通用户仅能访问自己的申请详情，无法查看他人申请。

## 7. 业务流程与状态机

### 7.1 申请状态机

```text
                  ┌──────────────────────────────┐
                  │                              │
   提交申请        ▼                              │
  ─────────► ┌─────────┐   管理员同意    ┌────────────┐
             │ 待审批   │ ─────────────► │  已通过     │（终态）
             │ pending │                └────────────┘
             └────┬────┘
                  │      管理员不同意   ┌────────────┐
                  ├───────────────────► │  未通过     │（终态）
                  │                     └────────────┘
                  │      用户撤回       ┌────────────┐
                  └───────────────────► │  已撤回     │（终态）
                                        └────────────┘
```

状态约定：

- 初始状态恒为「待审批」。
- 「已通过」「未通过」「已撤回」均为终态，不可再变更。
- 仅「待审批」状态可被撤回。

### 7.2 主流程：提交申请

1. 用户选择观测设备、填写起止时间。
2. 前端自动发起冲突预检；若冲突，列出占用申请并禁用提交。
3. 用户填写拍摄目标、目的与申请人信息后提交。
4. 服务端再次执行完整校验（字段、时间、设备）与冲突检测。
5. 校验通过则生成申请编号、写入申请记录与状态历史（submit），状态为待审批。
6. 申请立即出现在管理员的待审批队列中（按提交时间升序）。

### 7.3 主流程：审批

1. 管理员在待审批队列中选择一条申请，查看详情与状态历史。
2. 点击「同意」或「不同意」。
3. 选择「同意」时，系统再次检测该设备时段是否已被其他申请占用；若冲突，提示管理员并需要显式勾选「强制通过」。
4. 选择「不同意」时必须填写审批意见。
5. 确认后写入审批时间、审批人、审批意见，状态变更为已通过 / 未通过，并追加状态历史与审计日志。
6. 用户端刷新即可看到最新状态与完整历史。

### 7.4 冲突判定规则

两个申请构成冲突，当且仅当同时满足：

1. 属于同一台设备；
2. 双方状态均处于「待审批」或「已通过」（已撤回 / 未通过不占用时段）；
3. 时段存在重叠，即 A.开始 < B.结束 且 B.开始 < A.结束（半开区间，首尾相接不算冲突）。

## 9. 非功能需求

| 类别 | 要求 |
| --- | --- |
| 安全性 | 密码加盐哈希存储；SQL 全参数化；认证接口限速；防会话固定；CSV 公式注入防护；会话密钥与管理员密码支持环境变量注入 |
| 性能 | 单机支持中小规模使用（数十至数百用户、千级申请量）；列表查询分页；审计日志限制返回条数 |
| 可用性 | 关键操作有明确反馈；表单有内联校验；错误提示为可理解的中文文案 |
| 兼容性 | 桌面端与移动端主流浏览器（Chrome / Edge / Safari / Firefox）可用 |
| 可维护性 | 零原生依赖（SQLite 使用 Node 内置模块），无前端构建步骤，单命令启动 |
| 可移植性 | 数据存储为单个 SQLite 文件，便于备份与迁移 |

## 10. 约束与不做的事

明确不在本期范围内：

1. 不提供邮件 / 短信 / 站内消息通知，状态变更由用户主动查看。
2. 不提供管理员修改密码的界面入口（管理员密码由环境变量统一管理）。
3. 不提供申请内容的编辑功能（如需变更，撤回后重新提交）。
4. 不提供多级审批、审批人分配、代理审批等复杂审批流。
5. 不提供与望远镜控制系统或观测计划软件的对接。
6. 不提供多租户、多天文台隔离能力。
7. 不提供天气 / 云量联动与自动改期。

## 11. 验收标准

| 编号 | 验收项 | 通过标准 |
| --- | --- | --- |
| AC-1 | 角色隔离 | 普通用户无法访问任何管理员接口（403），未登录无法访问业务接口（401） |
| AC-2 | 申请闭环 | 提交 → 待审批 → 已通过 / 未通过的状态流转正确，用户端与管理端状态一致 |
| AC-3 | 冲突防护 | 同设备重叠时段无法提交（409）；审批时冲突需显式确认 |
| AC-4 | 撤回约束 | 仅本人、仅待审批状态可撤回 |
| AC-5 | 审批留痕 | 审批后能查询到审批时间、审批人、审批意见 |
| AC-6 | 历史完整 | 申请详情可查看全部状态变更记录，含提交与审批节点 |
| AC-7 | 统计准确 | 各状态数量与通过率与实际数据一致 |
| AC-8 | 导出可用 | CSV 可正常下载，中文不乱码，可用 Excel / WPS 打开 |
| AC-9 | 密码安全 | 数据库中不存储明文密码；错误密码无法登录 |
| AC-10 | 移动端可用 | 手机浏览器可完成「注册 → 提交申请 → 查看状态」全流程 |

## 12. 后续规划（未实现）

按优先级排列的候选增强项：

1. **通知能力**：审批结果站内信或邮件提醒。
2. **部署层安全**：HTTPS 强制、安全响应头（helmet）、会话持久化存储（替代内存存储）、CSRF Token。
3. **数据能力**：观测完成 / 取消 / 天气原因改期的扩展状态；设备利用率报表。
4. **协作能力**：申请备注与讨论、观测成果回传统计。
5. **体验优化**：日历视图升级为可视化时间轴、申请草稿、批量审批。
