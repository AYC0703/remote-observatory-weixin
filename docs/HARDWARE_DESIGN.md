# 观测站顶盖远程控制 —— 硬件接入设计

本文档描述「远程天文台使用申请审批及统计系统」如何从**纯审批系统**扩展为**能真正驱动硬件的系统**：管理员在微信小程序里为观测站接入远程控制，用户在**本人已批准的申请时段内**可以远程开合顶盖。

---

## 1. 设计目标与原则

| 原则 | 具体含义 |
| --- | --- |
| **开门要权限，关门要自由** | 开盖必须落在本人已批准的申请时段内；关盖是安全方向操作，任何登录用户随时可执行，不设权限 |
| **失效即安全（Fail-safe）** | 限位开关用常闭接法、断线即停机、控制器掉线保持位置 |
| **失联不关门** | 通信中断时**绝不**自动关盖——那会毁掉正在进行的整晚曝光，还可能撞到正在使用的望远镜 |
| **降雨是唯一无条件兜底** | 雨感走**设备本地硬逻辑**，不依赖网络、不依赖服务器 |
| **零新增依赖** | 通信采用设备主动 HTTP 长轮询，不引入 MQTT broker，不需要公网 IP 或端口映射 |
| **一切留痕** | 每条指令、每次操作、每个设备事件都进数据库与审计日志 |

---

## 2. 整体架构

```
┌──────────────────┐
│   微信小程序      │  观测站控制台 / 接入管理
└────────┬─────────┘
         │ HTTPS + Bearer Token（已有鉴权体系）
         ▼
┌──────────────────────────────────────────────┐
│  Node.js 后端 (server.js)                     │
│   ├─ /api/observatory/covers/*   用户指令       │
│   ├─ /api/admin/observatory/*    接入管理       │
│   └─ /api/observatory/device/*   设备端接口     │
│                                               │
│  hardware.js  安全联锁 · 指令队列 · 长轮询      │
│               · 自动关盖策略 · 事件流水         │
└────────┬─────────────────────────────────────┘
         │ SQLite（cover_* 四张表）
         ▼
   ┌───────────────┐   设备主动长轮询（出站 HTTP）
   │  ESP32 控制器  │◄──────────────────────────┐
   │  状态机 + 限位 │                           │
   │  过流 + 雨感   │──── 状态/回执/事件 ────────┘
   └───────┬───────┘
           │ PWM / GPIO
           ▼
   H 桥驱动器 ──► 电动推杆 ──► 顶盖
```

**为什么不用 MQTT：** MQTT 需要在服务器上多跑一个 broker、多一个进程要运维、多一个失效点，而且本项目只有一个后端、设备数量是个位数。HTTP 长轮询用现有 Express 就能实现，`curl` 就能模拟设备，联调与排障成本低得多。若将来设备数量增长到几十台，可平滑替换 `hardware.js` 的 `waitForCommand` 为 MQTT 发布订阅。

**为什么设备主动外连：** 观测站通常在校园网内、没有固定公网 IP、也不允许端口映射。设备主动出站 HTTP 天然穿透 NAT，且服务器地址变更时只需改固件配置。

## 3. 权限与安全联锁

### 3.1 开盖判定（`hardware.evaluateOpen`）

按顺序短路判定，任一不通过即拒绝并给出**可读原因**：

| # | 条件 | 拒绝理由 |
| --- | --- | --- |
| 1 | 设备未接入远程控制 | 该设备未接入远程控制 |
| 2 | 远程控制被停用 | 该设备的远程控制已停用 |
| 3 | 离线（超过 `COVER_OFFLINE_SEC` 秒无心跳） | 观测站离线…… |
| 4 | 降雨中 | 当前检测到降雨，禁止开盖 |
| 5 | 风速超限 | 风速 x m/s 超过上限 y m/s |
| 6 | 设备故障锁存 | 设备故障：xxx |
| 7 | 正在动作 | 设备正在动作中，请稍候 |
| 8 | 已开启 | 顶盖已处于开启状态 |
| 9 | 管理员 → **直接放行**（`elevated: true`） | 管理员权限 |
| 10 | 有覆盖当前时刻的已批准申请（可提前 `COVER_OPEN_GRACE_MIN` 分钟） | 申请 TEL-xxxx 生效中 |
| 11 | 否则拒绝，并提示最近一次申请的开始时间 | 你的申请 TEL-xxxx 于 … 开始，最早可提前 N 分钟开盖 |

### 3.2 关盖判定（`hardware.evaluateClose`）

只有两种情况拒绝：设备未接入、远程控制被停用。**顶盖已关闭**也会拒绝（409），避免无意义的指令堆积。

**在线状态不阻止关盖**：设备离线时关盖指令会排队（`COVER_CLOSE_TTL_SEC` 默认 1 小时），设备恢复连接后立即执行。

### 3.3 权限矩阵

| 场景 | 开盖 | 关盖 | 停止 / 复位故障 |
| --- | --- | --- | --- |
| 本人有生效中的已批准申请 | ✅ | ✅ | ✅ |
| 本人申请尚未开始（超过提前量） | ❌ | ✅ | ✅ |
| 完全无申请 | ❌ | ✅ | ✅ |
| 其他人在观测 | ❌ | ✅ | ✅ |
| 检测到降雨 | ❌ | ✅ | ✅ |
| 风速超限 | ❌ | ✅ | ✅ |
| 设备故障锁存 | ❌ | ✅ | ✅ |
| 观测站离线 | ❌ | ✅（排队） | ❌ |
| 管理员 | ✅（含强制通道） | ✅ | ✅ |

### 3.4 紧急关盖

`POST /api/observatory/covers/:id/emergency-close` 是**任何登录用户**都可调用的逃生通道：

1. 把该设备队列中所有 `pending` / `delivered` 指令置为 `superseded`
2. 以 `source = 'emergency'` 下发关盖
3. 写入审计日志与设备事件流水

### 3.5 管理员强制通道

`POST /api/admin/observatory/:id/command` **刻意绕过**在线、位置、故障等全部前置校验，仅用于应急。操作以 `source = 'admin-override'` 记录，并在设备事件流水中标为 `warn` 级别。

## 4. 通信协议

### 4.1 长轮询取指令

```
GET /api/observatory/device/poll?wait=4
X-Device-Token: cov_xxxxxxxx...
```

- `wait` 取值范围 `0 ~ COVER_POLL_MAX_SEC`（默认上限 50 秒），固件默认用 4 秒
- 有指令立即返回；无指令则挂起最多 `wait` 秒
- 有新指令入队时，服务器通过进程内 `EventEmitter` **立刻唤醒**挂起的请求，无需等待轮询周期
- 每次轮询都会刷新 `last_seen`，本身就是心跳

响应：

```json
{ "device": "望远镜A（0.5米）", "serverTime": "2026-10-02T14:22:21.366Z",
  "command": { "reqId": "c-c620855069102080", "action": "open",
               "issuedAt": "...", "expiresAt": "...", "source": "user" } }
```

### 4.2 上报状态

```
POST /api/observatory/device/state
```

```json
{ "position": "closed", "moving": false,
  "limitOpen": false, "limitClose": true,
  "rain": false, "wind": 3.4, "temperature": 18.2, "humidity": 71,
  "current": 320, "fault": "", "rssi": -58, "firmware": "1.0.0" }
```

字段为**部分更新**语义：未提供的字段沿用原值。`fault` 传 `""` 或 `null` 表示清除故障。

### 4.3 指令回执

```json
{ "reqId": "c-c620855069102080", "status": "acked", "detail": "已接收，开始开盖" }
```

`status` 取值：`acked`（设备已接收）/ `failed`（执行失败）/ `rejected`（设备拒绝，如正在动作中、降雨）。

### 4.4 事件上报

```json
{ "level": "error", "code": "STALL_OPEN", "message": "开盖堵转" }
```

`level` 为 `info` / `warn` / `error`；`error` 会额外写入审计日志。

## 5. 指令生命周期

```
        用户/管理员/自动策略
                │
                ▼
        [ pending ]  ── 超过 expires_at ──►  [ expired ]
                │
       设备长轮询取走
                │
                ▼
        [ delivered ] ── 超过 2×TTL 未回执 ──► [ timeout ]
                │
            设备回执
                │
        ┌───────┼────────┬───────────┐
        ▼       ▼        ▼           ▼
     acked   failed  rejected  superseded（被紧急关盖取代）
```

各指令的排队有效期：

| 指令 | 有效期 | 理由 |
| --- | --- | --- |
| `open` | `COVER_COMMAND_TTL_SEC`（90 秒） | 开盖有时效性，过期就该重新申请，不应在设备恢复后突然开盖 |
| `close` | `COVER_CLOSE_TTL_SEC`（1 小时） | 关盖是安全方向，设备恢复连接后越早执行越好 |
| `stop` / `clear-fault` | 同上（1 小时） | 同关盖 |

> **这是刻意的非对称设计**：开盖指令短命，关盖指令长寿。

## 6. 自动策略（`hardware.sweep`）

每 `COVER_SWEEP_MS`（默认 30 秒）执行一次，可用 `COVER_AUTO_CLOSE=false` 整体关闭：

| 触发条件 | 动作 |
| --- | --- |
| 设备**在线**且位置为 `open`/`moving`，且**检测到降雨** | 下发关盖（`auto-rain`），作为设备本地硬逻辑的第二道防线 |
| 设备**在线**且位置为 `open`/`moving`，且**没有任何生效中的申请**（含 `COVER_CLOSE_GRACE_MIN` 分钟宽限） | 下发关盖（`auto-schedule`） |

跳过条件：
- 设备离线 —— 不向失联设备下发指令，避免恢复连接后误动
- 队列中仍有 `pending` 指令，或 60 秒内刚有 `delivered` 指令 —— 避免叠加

> 旧版本曾把「任意 `delivered` 未回执的指令」都算作在途，导致一条无人回执的指令会把自动关盖卡住 3 分钟。现已改为只把「60 秒内下发的」视为在途。

## 7. 数据库

新增四张表，详见 `DATABASE_DESIGN.md`：

| 表 | 用途 |
| --- | --- |
| `cover_devices` | 已接入的观测站：设备令牌、实时状态、环境数据、心跳时间 |
| `cover_commands` | 指令队列与生命周期（`pending → delivered → acked/...`） |
| `cover_events` | 设备侧事件流水（堵转、超时、降雨、限位冲突……） |
| `cover_telemetry` | 环境采样历史（雨/风/温湿度），按 `COVER_TELEMETRY_MIN_SEC` 节流入库 |

设备重命名会级联更新 `cover_devices` / `cover_commands` / `cover_events` / `cover_telemetry` 的 `device` 列；设备被删除时 `cover_devices` 绑定一并删除。

## 8. 配置项

| 环境变量 | 默认值 | 说明 |
| --- | --- | --- |
| `COVER_OFFLINE_SEC` | `45` | 超过该秒数无心跳判定离线 |
| `COVER_OPEN_GRACE_MIN` | `10` | 可在申请开始前提前多少分钟开盖 |
| `COVER_CLOSE_GRACE_MIN` | `15` | 申请结束后的关盖宽限（此期间不自动关盖） |
| `COVER_COMMAND_TTL_SEC` | `90` | 开盖指令的排队有效期 |
| `COVER_CLOSE_TTL_SEC` | `3600` | 关盖 / 停止 / 复位指令的排队有效期 |
| `COVER_POLL_MAX_SEC` | `50` | 长轮询等待上限 |
| `COVER_WIND_LIMIT` | `12` | 风速上限（m/s），超过禁止开盖 |
| `COVER_AUTO_CLOSE` | `true` | 设为 `false` 关闭自动关盖策略 |
| `COVER_SWEEP_MS` | `30000` | 自动策略扫描间隔 |
| `COVER_TELEMETRY_MIN_SEC` | `120` | 环境采样最小入库间隔 |

## 9. 硬件侧要求（摘要）

完整接线、标定与烧录步骤见 `firmware/cover-controller/README.md`。

**必须做到：**

1. **限位开关常闭（NC）接法**，断线即停机
2. **机械硬限位**，即使电气全失效也撞不出去
3. **雨感本地硬逻辑**，不经过网络
4. **过流/堵转保护**，关门受阻必须反转退让（防夹）
5. **急停按钮**串在驱动器供电回路上
6. **手动应急**（手摇柄或离合器）
7. **IP65 防水接线盒**与防水接头
8. 电机电源与 ESP32 电源**独立降压 + 光耦隔离**，电机线加磁环

**绝对不要：**

- 用 L298N 之类的 2A 驱动器（推杆堵转瞬间可达 15A+）
- 失联自动关门
- 只靠软件限位
- 把 5V 传感器信号直接接进 GPIO（ESP32 是 3.3V）

## 10. 已知限制与后续方向

| 限制 | 建议改进 |
| --- | --- |
| 长轮询等待 4 秒，空闲时指令延迟最长约 4 秒 | 拆成双 FreeRTOS 任务后可把等待提到 25 秒，延迟降到毫秒级 |
| 固件无 OTA | 接入 `ArduinoOTA` 或 `esp_ota`，否则每次改固件都要上屋顶 |
| 设备端未校验 TLS 证书 | 公网部署时改用 `WiFiClientSecure` + `setCACert()` |
| 无小程序订阅消息推送 | 故障、降雨关盖、时段自动关盖应推送通知到用户 |
| 无设备端时钟 | 事件时间以服务器接收时间为准；如需精确可加 NTP |
| 单点后端 | 后端宕机时设备仍能本地按钮操作与雨感保护，但无法远程控制 |
